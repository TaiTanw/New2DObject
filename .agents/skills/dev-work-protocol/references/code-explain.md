# 代码解释

**何时读：** 用户询问代码的具体情况；或结构验证完工后需要说明结构关联。

核心：用代码解释逻辑。文本回复不宜膨胀。若用户需进一步清楚结构，则以图表示。

## 回答形态

1. 先给阅读入口：文件路径、类型名、方法名。需要时用代码引用，不要复述整段实现。
2. 文本只做指引：从哪个符号看到哪个符号，以及「为什么是这一级变动」。
3. 用户仍看不清结构时，出 drawio，不要继续加长说明。图的存放见 [docs-and-artifacts.md](docs-and-artifacts.md)。
4. 闭环很小的简单问题（某个字段现在谁写谁读）可以直接用一两句回答。

流程验证的完工汇报 **不是** 本文件：那个模式不解释代码。仅当用户另外问起时才进入本文件。

## 变动等级

按开工后代码的实际变动，核对必要程度如下。序号越大，结构变动越大。结构变动不等于代码量。大数字通常默认包含小数字（例如新增类通常一定会新增字段）。

汇报时给出 **最高等级**，并覆盖它所包含的小等级该说的原因。

### 1. 只增减字段，改动方法实现和参数

说明是由于 **数据来源的变动**，还是 **层级抽象方面的职能变化**。

- 数据来源：这个值改从别的快照、接口或配置来，调用点还在原层。
- 职能变化：字段不再属于原来那个对象该知道的事，或读写权限跨层了。

指到字段和被改的方法即可。

### 2. 增减方法，或方法改名

说明是单纯为了 **结构清晰的划分**，还是 **类对外窄口的变化**。

- 结构清晰：私有步骤拆分、命名更贴切，对外契约几乎不变。
- 对外窄口：谁可以调用、必须经过哪一层、公开表面变了。

指到新旧方法名，以及还剩哪几个对外入口。

### 3. 文件结构变化

通常需要与人核对。说明是 **文件整理**，还是 **框架的变化**。

- 文件整理：类型搬家、拆文件，职责和调用关系基本不变。
- 框架变化：新层、新程序集边界、时序槽增减、谁拥有关系变了。

这一级默认同时说明字段与方法侧的要点，然后出图或等用户核对，不要只丢一份文件清单。

## 和开工模式的衔接

- **结构验证**：优先等级 2/3 的阅读路径；改动太大或用户无从下手时出图。
- **执行落地**：只解释超出用户思路的那一段对应的等级。
- **流程验证**：用户没问代码时不主动用本文件。
