# 正式开工前分类

**何时读：** 已经明确开工（实现、修改、补齐、接入、按指定范围开发）。

按照用户对 **AI 即将书写的代码** 的了解程度分成 3 种。分类未必严谨，以用户当场指定为准；未指定则先问一句。落不进三类则走第 4 节，不准开工。

写代码时的注释与忽略范围见 [implementation.md](implementation.md)。完工后的代码说明见 [code-explain.md](code-explain.md)。

## 1. 流程验证

完全不在乎代码怎么写，只关注是否越界和流程是否跑通。

典型：物理层数据关联已经完成，用户指定范围，让 AI 用传入的物理数据解释不同动画切换。只关心跳跃、下落等逻辑下动画是否正确播放，以及是否严格停在划分范围内。

开工时：

- 先复述范围：改哪些层/文件类型，明确不碰什么。
- 按用户指定的输入数据接线，不扩展数据源，不顺手补框架。
- 不向用户推销「更好的结构」，除非范围本身跑不通。

开发完成后，主要回答开发情况：

- 是否顺利
- 是否缺少关键数据
- **不回答代码具体做了什么**

用户若接着问代码细节，那是新的「代码解释」轮次，不要在本模式完工汇报里主动展开。

## 2. 结构验证

知道当前的缺口或者需求，但不清楚代码具体要怎么安排。完工后需要知晓代码全部情况。AI 按自己的思路开工。主要在需求未完全核对、但仍需 AI 拓展思路时使用：开工的同时用代码回答用户疑惑。

典型：知道要增加接口，但模模糊糊不清楚数据结构如何安排；或用户用最简单思路当草稿，几轮核对仍不清楚为什么不用用户的方法，则 AI 直接按自身能力开发。

开工时：

- 用最短文字写下将要落下的结构（类型、归属层、数据从哪进哪出），然后直接写。
- 不要用长文替代实现。用户要的答案在代码里。
- 若用户草稿与将要采用的结构冲突：采用能守住原则的结构，完工后用代码对照，而不是开工前再辩一轮。

开发完成后，主要回答：

- 代码得从哪里看
- 怎么从开工前的结构逐步与当前结构关联

核心在于 **用代码回答问题**。AI 文本只做指引。若单次代码改动太多，或用户自身无从下手阅读，则制作 drawio，并转入「代码解释」。

要么代码回答，要么 drawio 图形回答；文本只做指引，以及闭环很小的简单问题。

## 3. 执行落地

用户清楚知道需求和实现，AI 只做基本执行。开工后仍需掌握全部代码情况，但开工前已经基本确认好代码结构甚至字段名称。

开工时：

- 按已确认的结构/字段落地，不改名「为了更漂亮」。
- 发现必须新增用户未点名的结构时，做得最小，并在完工时单独列出。
- 发现用户判断与现码冲突：先按能跑通且不越界的方式做完，再在完工时纠正，而不是停工空转。

开发完成后，主要回答 **除去用户思路以外，新增的结构**。

例如：用户知道数据链路，但开工后把部分字段收束为类或结构体——着重说明结构变化。或者开发后发现用户判断出错，需要纠正。

不要把用户已经指定的字段清单再讲解一遍。

## 4. 不属于三类时：退回需求核对

若不属于上述情况，不要写代码。例如：用户说明确开工，但对当前结构几乎不明白，且还要求通读开工后代码。此时同时具备「结构几乎不明白」和「完工后要通读全部代码」，还没有收敛到任何一类。

返回需求核对，进一步收敛，直到属于三种分类之一：

- 当前要解决的是哪一条事务（编号与 0.1 单位落文档，见 [work-tracking.md](work-tracking.md)）
- 验收是什么、范围停在哪一层
- 用户对即将书写的代码了解到哪一步：不在乎写法 / 知道缺口但不会安排 / 结构和字段已确认
- 开工后需要掌握代码到什么程度：不解释代码 / 用代码或图看懂结构 / 只看超出用户思路的结构

未落入 1/2/3 之前，只做核对，不开工。

## 完工时不要混用汇报

| 模式 | 汇报 | 不要做 |
|------|------|--------|
| 流程验证 | 顺不顺利、缺不缺数据 | 讲实现、贴长 diff 说明 |
| 结构验证 | 从哪看、如何从旧结构连到新结构 | 用长文代替代码/图 |
| 执行落地 | 新增结构，或纠正用户判断 | 复述用户已经确认的设计 |
