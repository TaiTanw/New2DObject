# 文档归属和清理

**何时读：** 要更新文档、或代码解释需要出图时。

本协议不保存专题设计正文。路径 **只读** [SKILL.md 第 6 节](../SKILL.md) 的填写框，不要在本文件再抄一份。未填则先问用户。

## 稳定文档（按职能找，不按固定文件名）

先打开填写框里的文档索引。缺哪一类，以索引和填写框为准。

| 职能 | 怎么找 | 何时改 |
|------|--------|--------|
| 框架总览、分层、主数据流 | 索引里的总览与结构图 | 层级或主数据流真的变了 |
| 文档索引 | 文档入口本身 | 新增或移动了稳定文档/图 |
| 专题设计 | 索引列出的专题正文 | 该专题的已拍板边界、阶段结论变了 |
| 功能与漏洞事务 | 索引里的事务表（一/二/三） | 出现漏洞、增减功能、或用户要求整理回收 |
| 局部功能说明 | 靠近对应代码的说明文件 | 该功能的使用范围或数据入口变了 |

不要为一次实现新开平行长文。能补进已有文档的，不新建文件。

功能与漏洞的 **编号规则** 见 [work-tracking.md](work-tracking.md)。skill 只回答当前是什么问题、怎么分类；题述写在填写框指定的事务表里。

## 代码解释用的临时图

结构验证或代码解释需要图时，放到填写框中的「临时解释目录」。该项未填则先问用户；不要默认编一个目录名。

规则：

- 这是临时产物，用来让人看清开工前后结构如何关联，不是新的设计权威。
- 一图只回答本轮结构问题，不要重画整份框架图。已有结构图时，只画相对它多出来的那一块。
- 文本回复只给路径和从哪看，不把图再翻译成长文。
- 用户核对后：仍有长期阅读价值 → 移到稳定文档区并挂上索引；否则删除。
- 不要把临时图画进 skill 目录，也不要散落在仓库根目录。

未出图前不要预先建空目录。

## 待处理事务表（功能 / 漏洞）

出现漏洞或增减功能时，按下面三块维护。这是文档模板，不是 skill 里的问题清单，也不是某个固定文件。

### 一、当前待处理事务

| 问题编号 | 问题简述 | 优先程度 | 当前进展 | 实际情况 / 评估 |
|----------|----------|----------|----------|-----------------|
| `V_2` | 一句话 | 漏洞：`P0` / `P1` / `已修复`。功能：是否拍板、是否模糊、是否退化等 | 进行到哪 | `0.1`、`0.2` 等开工单位。内容不多写在本列或「二」；多则单开文档，本列只留索引 |

一处里也可以留着已完成或已冻结的条目。**只有用户明确要求整理和回收时**，才把它们搬进「三」。

### 二、具体描述

按问题编号做标题，下面写描述。对应 `V_2`、`F_1` 等，不要把 0.1 单位散写成互不相关的新问题。

### 三、历史事务

已完成、已冻结、已退化等回收后的事务。未接到整理/回收指令时，不要主动搬家。

## 和开工模式的关系

- 功能与漏洞安排：只改事务表（分类、优先级、0.1 拆分）。未明确开工前不改代码。
- 流程验证：默认不改设计文档，不产出解释图；若该 0.1 改变了事务进展，只更新事务表对应行。
- 结构验证 / 代码解释：优先临图；只有框架级结论变了才动稳定文档。
- 执行落地：若新增了用户未指定的结构，把结构变化写进该改的那一份稳定文档，而不是另写一份「开发笔记」。
