# 08 — 第一阶段：运动快照与预测/提交一致性

本次实现范围是第一阶段的运动快照。环境接口整理、接触生命周期、速度回写及多箱迭代仍属于后续工作。

## 1. 本次修改解决什么

原相位 3 用 `GetPlanarVelocity() * dt` 预测 AABB，相位 5 才进行地面切线处理和平台位移补偿。斜坡或移动平台上，两次计算使用的基础位移不同。

现在由实体在相位 3 构建一次 `EntityMotionFrame`，预测和提交复用其中的 `plannedWorldDelta`。原相位 5 的地面位移公式原样提取，接触力算法、静墙裁剪和 Dynamic 刚体模式保持现有实现。

改变的是预测所依据的基础运动。相同速度、地面及平台输入下，基础提交位移保持原规则；由于接触候选位置改变，实际接触偏置及随后运动结果可能随之变化。

## 2. 职能与数据归属

| 结构/方法 | 职能及生命周期 | 本次变化 |
|---|---|---|
| `PlayerPhysicsData` | 实体已有速度状态，由速度阶段和事件处理写入 | 字段及入账方式不变 |
| `EntityMotionFrame` | 实体持有的本帧未约束运动快照；相位 3 整体替换 | 只读值结构；正式运行保存 `plannedWorldDelta`，其余分量作为 EditorOnly 观测副本 |
| `BasicEntity.BuildMotionFrame` | 将已采样的速度、几何、平台及步长转换为快照 | 新增纯计算方法，从原相位 5 提取地面位移公式；不另行积分力或写 Unity 世界 |
| `PhysicalBoundingBox` | 向管理器上报预测中心、半长宽和实体引用 | 字段不变；中心改为当前 Collider 中心加 `plannedWorldDelta` |
| `EntitySolutionResult` | 相位 4 累加、本帧相位 5 消费的接触纠偏 | 仍只有 `displacementOffset`，不保存基础运动或跨帧速度 |
| `EntityPhysicsDebugSnapshot` | 编辑器只读观测结果 | 基础运动字段改从运行时运动快照复制，新增 `plannedWorldDelta` |
| `PlayerDataWindow` | 展示实体提供的快照 | 新增“预测/提交共用基础位移”，不参与运行时计算 |

`EntityMotionFrame` 放在现有 `Physics/Data/Struct.cs`，本轮没有迁移序列化字段或新增场景组件。

快照字段的区别：

| 字段 | 含义 |
|---|---|
| `debugFreeVelocity` | EditorOnly：速度结算后的原始合量，尚未应用地面位移规则 |
| `debugIntegratedVelocityDelta` | EditorOnly：原始 `freeVelocity * fixedDeltaTime` 的副本 |
| `debugMotionDelta` | EditorOnly：按原有地面规则处理后的实体位移副本，不含平台 |
| `debugPlatformDelta` | EditorOnly：本帧着地平台位移的副本；离地时为零 |
| `plannedWorldDelta` | `motionDelta + platformDelta`，在构造时合成一次 |

这些字段不是可以全部相加的速度/位移来源。速度积分和地面处理表达前后两种阶段；构建方法中的运行时局部量 `motionDelta + platformDelta` 组成基础位移，四个 debug 字段只供解释来源。格式约定见 [05 §4.1](./05-数据语义与调试约定.md#41-editoronly-命名与代码格式)。

## 3. 本帧调用顺序

```text
相位 1：GeometricQuery
相位 2：PhyFunUpdate
相位 3：SpeedCalculation
          → 原有水平/竖直速度计算（含上一帧接触动态力）
          → 采样地面法线、着地状态、平台 Delta、fixedDeltaTime
          → BuildMotionFrame，整体替换实体 motionFrame
          → PositionPrediction
              清零本帧接触偏置
              Collider 中心 + motionFrame.plannedWorldDelta → 预测 AABB
相位 4：ContactForSolution
          → 本帧 displacementOffset
          → 原有下一帧接触动态力
相位 5：DisplacementCorrection
          → motionFrame.plannedWorldDelta + displacementOffset
          → 原有静墙裁剪
          → 刷新已解析的墙滑引用、记录编辑器观测值
          → 一次 MovePosition
下一帧：采集实际位置及 engineCorrection
```

相位 5 不再重新计算速度积分、斜坡切线或平台补偿；平台位移因此不会在预测和提交时重复相加。

`MovePosition` 保持为相位 5 回调的最后一条语句。墙滑引用来自此前已解析的静墙状态，更新放在提交前，不依赖提交后的真实几何；Unity 对移动请求的物理执行仍发生在后续模拟中。

“预测与提交一致”指二者的基础位移相同。接触纠偏、静墙裁剪和 Unity 后续修正仍会让最终落点不同于最初预测，不能要求二者最终位置始终相等。

现有水平接触施力仍读取 `GetPlanarVelocity()`，没有改为 `plannedWorldDelta / dt`。本轮没有实现新的接触速度算法。

## 4. 明确保留的竖直环境速度问题

`BuildMotionFrame` 的着地分支已用 TODO 注释标注以下事实：

```text
原始竖直合速度 = verticalSpeed + phyVSpeed

空中：motionDelta.y 使用原始竖直合速度

着地：先以 verticalSpeed * dt 重建竖直位移
      再加地面切线运动
      不加入 phyVSpeed

平台：platformDelta.y 另行加入
```

`verticalSpeed` 含自研重力和跳跃累计，不应按字段分组把它理解成纯主动目标。`phyVSpeed` 与平台 Y 位移来自不同链路，平台位移不能替代被省略的竖直环境速度。

本次既不补加 `phyVSpeed`，也不清零它；只让预测遵循现有提交规则。调试窗口仍能通过“速度积分位移”和“斜坡修正后位移”的差异观察该情况。

后续必须单独核对这些场景，再决定是否以及如何修改规则：

1. 平地静止时，正向竖直环境速度是否应使实体离地。
2. 平地静止时，负向竖直环境速度是否应被地面约束抵消。
3. 起跳首帧几何仍报告着地时，环境速度如何参与。
4. 斜坡切线具有 Y 分量时，如何区分地面运动与竖直外部速度。
5. 升降平台与竖直环境速度同时存在时，二者如何组合。

这些是待决定的玩法/运动约束规则，不以当前行为等价检查代替策略验收。

## 5. 本轮验证及限制

- 使用项目现有 Unity Roslyn 响应文件完整编译运行时与编辑器程序集，均通过；验证输出写入忽略目录 `Temp/MotionSnapshotValidation`。
- 对实际编译的 `BasicEntity.BuildMotionFrame` 和 `EntityMotionFrame` 执行 23 项检查，覆盖空中正负环境速度、着地省略竖直环境速度、起跳首帧、15° 斜坡双向运动、相反坡向、平台补偿、不同步长及快照只读性。
- 数值检查确认着地规则按现状保留，不表示该规则已经被认定为正确设计。
- EditorOnly 格式整理后，重新通过运行时/编辑器程序集编译，并通过移除 `UNITY_EDITOR` 系列符号的运行时代码编译检查；该项用于验证观测字段隔离，不是完整 Player 构建。
- 尚未完成 Unity Play Mode 的斜坡推箱、升降平台和接触手感验收。预测一致性修复不等于接触轴、skin/释放阈值、多箱传播及 Unity 二次修正全部解决。

人工验收时观察“预测/提交共用基础位移”“接触对偏置”“静墙裁剪前位移”“最终请求位移”“引擎修正量”。先区分基础运动、接触纠偏与引擎修正，再判断剩余问题。
